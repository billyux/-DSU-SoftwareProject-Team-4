## 1. 한 줄 요약

점수 계산(`docs/동네 진단 서비스 정주여건 점수 계산 방식.md`)에서 시설 유형별 가중치를 쓰기 위해
`facilities.facility_type` 값을 세분화했고(예: `소매` → `편의점`, `약국` …), 가중치는 **DB 테이블**에
**페르소나(개인/가족/노인)별로** 저장해서 관리자 페이지에서 재배포 없이 고칠 수 있게 했습니다.
점수 계산 엔진도 구현되어 있습니다.

## 2. 전체 구조

```
facilities (시설 8,350건)                     ← facility_type으로 연결
   │
   ├─ persona_facility_type_weights  페르소나 × facility_type → (점수 카테고리, wᵢ)
   ├─ persona_category_weights       페르소나 × 점수 카테고리 → W_c
   └─ category_params                점수 카테고리 → 반경 r_c, 목표 개수 n_c (페르소나 공통)
          │
          ▼
backend/app/services/neighborhood_score.py  calculate_score(lat, lng, db, persona)
          │
          ▼
GET /api/score?address=...&persona=...   ·   GET /api/score/point?lat=..&lng=..&persona=...
```

| 위치 | 역할 |
| --- | --- |
| `backend/app/models.py` | `Facility`, `CategoryParam`, `PersonaCategoryWeight`, `PersonaFacilityTypeWeight` |
| `backend/app/services/neighborhood_score.py` | 점수 계산 엔진 (거리 감쇠, 포화 함수, 종합병원 최근접 거리) |
| `backend/app/seed_weights.py` | 가중치 초기값을 DB에 넣는 스크립트 (**테이블이 비어 있을 때만** 동작) |
| `backend/app/routers/admin_weights.py` | 가중치 조회·**수정** API (`/api/admin/weights/...`). 추가·삭제 API는 없음 |
| `frontend/src/pages/AdminPage.jsx` | 페르소나 선택 + 가중치 편집 화면 |
| `data/scripts/clean_facilities.py` | 시설 원본 → `data/processed/facilities.csv` |
| `backend/app/load_facilities.py` | `facilities.csv` → DB (`--replace`면 비우고 전부 다시 넣음, 300건씩 나눠 커밋) |

> 예전에 있던 `backend/app/services/facility_weights.py`(코드 안의 가중치 표)는 **삭제되었습니다**.
> 가중치는 이제 DB 테이블에만 있습니다.

## 3. `facility_type` 세분화 방식

컬럼 구성(`id, category, facility_type, name, latitude, longitude, source`)은 처음부터 그대로이고,
`facility_type` 값만 구체적인 유형 이름이 되었습니다 (현재 147종류).

| 출처 | 건수 | `facility_type` 정하는 방법 |
| --- | --- | --- |
| 상가업소정보 (소상공인시장진흥공단) | 6,316 | 업종 **소분류** (`편의점`, `카페`, `노래방` …). 원본에서 같은 가게(같은 상호명·같은 대분류·100m 이내)를 찾아 붙임 |
| 병원정보 (건강보험심사평가원, HIRA) | 243 | 종별(`종합병원`, `치과의원` …). 종별이 `의원`이면 **이름으로 진료과 판별** (`김내과의원` → `내과/소아과 의원`, 판별 불가 → `기타 의원`) |
| 학교 (한국교육시설안전원) | 35 | 학교급 (`초등학교`, `중학교`, `고등학교`) |
| CCTV / 버스정류장 / 지하철역 / 노인교실 | 1,081 / 659 / 7 / 9 | 고정값 (`cctv`, `버스정류장`, `지하철역`, `노인교실`) |

- **상가 목록은 처음 DB에 넣은 목록 그대로 유지합니다.** 상가 원본을 API로 새로 받으면 폐업하거나 새로 생긴 가게가
  섞이므로, `clean_facilities.py`는 기존 `facilities.csv`의 상가 목록을 기준으로 두고 원본에서 소분류만 찾아 붙입니다
  (`attach_store_subtypes`). 원본에서 못 찾은 가게는 기존 값을 그대로 둡니다.
- **상가의 `보건의료` 91건은 일부러 세분화하지 않았습니다.** 같은 병원이 HIRA 데이터에도 있어서, 둘 다 세분화하면
  의료 점수가 두 번 들어가기 때문입니다. 가중치 테이블에 `보건의료`가 없으므로 점수에서 자동으로 빠지고,
  의료 점수는 HIRA 병원만으로 계산됩니다. 지도에는 둘 다 보입니다.
- `category`(`안전` / `생활편의` / `음식점` / `교통`)는 그대로이며, 지도에서 시설 점의 **색**을 정하는 데 씁니다
  (`frontend/src/pages/SafetyMapPage.jsx`의 `CATEGORY_COLORS`).

## 4. 가중치 초기값 (`seed_weights.py`, 세 페르소나 모두 같은 초안 값)

AHP 설문 결과가 나오기 전이라 개인/가족/노인 모두 같은 값입니다. 결과가 나오면 관리자 페이지에서 페르소나별로 고칩니다.

| 점수 카테고리 | 반경 r_c | 목표 개수 n_c | W_c | 해당 facility_type (wᵢ) |
| --- | --- | --- | --- | --- |
| 안전 | 300m | 4 | 0.20 | `cctv` (1.0) |
| 의료_의원급 | 500m | 2 | 0.25 (의료 전체) | `내과/소아과 의원` (0.6), `피부/비뇨기과 의원` (0.1), `성형외과 의원` (0.1) |
| 의료_종합병원 | 5,000m (최근접 검색 반경) | – | 0 (의원급에 합산) | `종합병원` (1.0) |
| 생필품 | 400m | 3 | 0.20 | `슈퍼마켓`, `편의점`, `약국` (각 1.0) |
| 버스 | 400m | 2 | 0.15 | `버스정류장` (1.0, 경유 노선 수는 고려 안 함) |
| 지하철 | 800m | 1 | 0.20 | `지하철역` (1.0) |

가중치 테이블에 없는 유형(학교, 노인교실, 카페, 치과의원, 외과 의원 등)은 **지도에는 보이지만 점수에서는 빠집니다.**

## 5. 새 시설 데이터를 추가할 때

### 5-1. 시설 데이터 넣기

1. `clean_facilities.py`의 `main()`에 블록을 추가합니다. 기존 블록(학교, 노인교실 등)과 같은 형태로
   `standardize()`를 써서 공통 스키마로 바꾸고, 원본이 없을 때를 위해 `else`에 `_reuse_processed(...)`를 둡니다.
2. `category`는 `안전` / `생활편의` / `음식점` / `교통` 중 하나를 씁니다. 새 값을 쓰면 지도에서 기본 색으로 나오므로
   `CATEGORY_COLORS`도 같이 추가합니다.
3. `facility_type`은 구체적인 유형 이름으로 정합니다 (예: `어린이집`).
4. 이미 있는 데이터와 같은 시설이 겹치는지 확인합니다. 겹치면 한쪽만 점수에 반영되도록, 다른 쪽은
   가중치 테이블에 없는 `facility_type`으로 둡니다 (상가 `보건의료` 처리 방식 참고).
5. `python data/scripts/clean_facilities.py`로 CSV를 다시 만들고, 실행 로그에서 다른 데이터셋의 건수가
   줄지 않았는지 확인합니다. 원본 CSV(`data/raw/`)는 git에 올라가지 않아서 PC마다 없을 수 있는데, 그때는
   `원본 파일 없음 -> 기존 facilities.csv의 N건 재사용`이 뜨는 게 정상입니다.
6. DB 소유자가 `backend` 폴더에서 `python -m app.load_facilities --replace`로 DB에 반영합니다.

### 5-2. 점수에 반영하기 (가중치 추가)

**관리자 페이지와 API로는 가중치를 "수정"만 할 수 있고 "추가"는 못 합니다.** `seed_weights.py`도 테이블이
비어 있을 때만 값을 넣기 때문에, 이미 값이 있는 지금 DB에서는 스크립트에 줄을 추가해도 반영되지 않습니다.
새 유형을 점수에 넣으려면:

- **기존 점수 카테고리에 넣을 때** (예: `치과의원`을 `의료_의원급`에): `persona_facility_type_weights`에
  **개인/가족/노인 세 페르소나 각각** 한 행씩 추가합니다. `facility_type`은 `facilities`의 값과 **글자 하나 틀리지 않게**
  같아야 합니다.
- **새 점수 카테고리를 만들 때** (예: `교육`): 위에 더해 `category_params`에 한 행, `persona_category_weights`에
  페르소나별로 한 행씩 추가하고, **페르소나마다 W_c 합이 1이 되도록** 기존 값도 조정합니다.
- 이후 `seed_weights.py`의 초기값 목록에도 같은 내용을 적어서, DB를 새로 만들 때도 같은 값이 들어가게 합니다.

## 6. AI 작업 규칙 (팀원이 쓰는 AI 도구용)

- **가중치를 `facilities` 행에 컬럼으로 저장하지 말 것.** 가중치는 `persona_facility_type_weights` /
  `persona_category_weights` / `category_params` 테이블에서만 관리한다.
- **가중치는 페르소나(개인/가족/노인)별로 따로 저장된다.** 새 유형이나 카테고리를 추가할 때 세 페르소나 모두에 행을 넣을 것. 하나라도 빠지면 그 페르소나 점수에서만 조용히 빠진다.
- **`seed_weights.py`를 고치는 것만으로는 기존 DB에 반영되지 않는다.** 테이블이 비어 있을 때만 동작한다. 기존 DB에는 행을 직접 추가해야 한다.
- **`facility_type` 이름을 바꾸면 `persona_facility_type_weights`의 같은 이름도 같이 바꿀 것.** 이름이 어긋나면 에러 없이 점수에서 빠진다.
- **상가 가게 목록을 API 원본으로 다시 만들지 말 것.** 목록은 기존 `facilities.csv`(= DB)를 유지하고, 원본은 소분류를 붙이는 데만 쓴다(`attach_store_subtypes`).
- **상가 `보건의료`를 세분화하지 말 것.** HIRA 병원과 중복되어 의료 점수가 두 번 들어간다.
- **기존 `category` 값을 바꾸지 말 것.** 지도 색 구분(`CATEGORY_COLORS`)이 이 값에 의존한다.
- **기존 테이블에 컬럼을 추가할 때는 Turso DB에 먼저 반영한 뒤 코드를 푸시할 것.** `Base.metadata.create_all`은 **새 테이블은 만들어주지만, 이미 있는 테이블에 컬럼을 추가하지는 않는다.** 배포 서버(Render)도 같은 Turso DB를 쓰므로, 코드만 먼저 올라가면 `no such column` 에러로 배포 사이트가 깨진다.
- **로컬 테스트는 Turso가 아니라 로컬 SQLite로 할 것.** `DATABASE_URL='sqlite:////tmp/test.db'`를 지정해서 실행하면 `backend/.env`의 Turso 주소보다 우선한다(`load_dotenv`는 이미 설정된 환경변수를 덮어쓰지 않음). `--replace`처럼 데이터를 지우는 명령은 실행 전에 `engine.url`이 SQLite인지 확인한다. 로컬 SQLite에서 점수를 계산하려면 `python -m app.seed_weights`도 먼저 실행해야 한다.
